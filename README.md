## 1. Постановка задачи

### Цели работы

### Индивидуальное задание

Написать модульные тесты к проекту интернет-магазина мягкой мебели, разработанному в лабораторной работе № 2. Проверить как отдельные компоненты (модели, контроллеры, шаблоны, маршруты, настройки) в изоляции, так и их совместную работу.

## 2. Краткое описание тестируемого проекта

Тестируется Django-проект магазина мягкой мебели с корзиной (разработка — лабораторная работа № 2). Основные сущности и функциональность, на которые направлены тесты:

- Модели (shop/models.py): Category, Product, Purchase, Cart, CartItem. Бизнес-логика корзины вынесена в методы Cart.add, remove, clear, contains, product_ids, summary, total_price.
- Каталог (/, /?category=<id>) с фильтром по категории.
- Корзина (/cart/): добавление, удаление, очистка товаров; подсчёт итоговой стоимости и количества; ограничение «один экземпляр одного товара» (на уровне кода и СУБД через UniqueConstraint(cart, product)); привязка корзины к сессии.
- Покупка «сразу» (/buy/<id>/) — сохранена из исходного проекта.
- Админка (/admin/): регистрация моделей, методы CartAdmin.
- Маршрутизация (shop/urls.py), context processor (счётчик и сумма корзины в шапке страниц), конфигурация (tplab2/settings.py).

Изменяющие запросы принимаются только методом POST и защищены CSRF-токеном.

## 3. Используемые технологии

- Python 3 — язык программирования.
- Django — фреймворк; тестовый клиент, TestCase, SimpleTestCase, RequestFactory, override_settings.
- PostgreSQL — СУБД; драйвер psycopg2.
- unittest / django.test.TestCase — модульные и интеграционные тесты.
- unittest.mock (MagicMock, patch, PropertyMock) — изоляция зависимостей.
- coverage — измерение покрытия строк и ветвлений.

## 4. Подход к тестированию

Тесты разделены на два уровня.

### Юнит-тесты

Проверяют одну единицу кода (функцию, метод, шаблон) отдельно от остальных. Наследуются от SimpleTestCase, который запрещает любые запросы к БД: если тест случайно обратится к базе, он упадёт. Зависимости заменяются заглушками из unittest.mock.

- test_unit_views.py — контроллеры; модели, get_cart, messages и render заменены моками; проверяются вызовы и передаваемый в шаблон контекст.
- test_unit_models_isolated.py — методы Cart.add, remove, clear, contains, product_ids, summary; менеджер items и CartItem заменены моками.
- test_unit_cart_and_processor.py — get_cart и context processor.
- test_templates.py — шаблоны отрисовываются через render_to_string с подставленными данными.
- test_urls.py, test_apps_and_settings.py — маршрутизация и конфигурация.
- ModelMetaTestCase и ModelStrWithoutDatabaseTestCase в test_model_validation.py — метаданные моделей и __str__.

### Интеграционные тесты

(TestCase с реальной БД PostgreSQL) проверяют совместную работу компонентов: SQL-запросы, ограничение уникальности, сессии, сообщения, CSRF. К ним относятся test_models.py, test_views.py, test_fixtures.py, test_model_validation.py (проверка full_clean), test_scenarios.py и остальные файлы без пометки «unit».

### Применяемые приёмы

- изоляция зависимостей — mock, patch, PropertyMock;
- граничные значения — длина строк 200/201 и 100/101 символов, цена 0, −1, 2147483647 и 2147483648;
- негативные сценарии — несуществующий товар, повторное добавление, GET вместо POST, запрос без CSRF-токена, чужой адрес в next, устаревший идентификатор корзины в сессии;
- проверка контрактов — ограничение уникальности корзины, on_delete, соответствие миграций моделям;
- сквозной сценарий покупателя от пустой корзины до очистки.

## 6. Запуск тестов и покрытие

Django создаёт для тестов отдельную базу test_django_db и удаляет её по окончании, поэтому у пользователя PostgreSQL должно быть право CREATEDB.

```text
python manage.py test shop/tests/                  # все тесты
python manage.py test shop.tests.test_unit_views   # один модуль
```

### Покрытие кода

```text
pip install coverage
coverage run manage.py test shop/tests/
coverage report                                    # покрытие строк и ветвлений (настройки в .coveragerc)
coverage html                                      # подробный отчёт в htmlcov/
```

## 7. Выводы

- Именно благодаря разделению MVC удалось написать юнит-тесты: контроллеры, модели и шаблоны проверяются независимо друг от друга.
- Юнит-тесты с заглушками быстрые и точно указывают на сломанный участок кода, но проверяют только вызовы и не видят ошибок в реальных SQL-запросах. Интеграционные тесты на PostgreSQL, наоборот, находят такие ошибки, но медленнее и сложнее в диагностике. Поэтому в проекте нужны оба уровня.
- SimpleTestCase страхует изоляцию: тест с запросом к БД падает сразу, не давая случайно превратить юнит-тест в интеграционный.
- Тест синхронности моделей и миграций страхует от забытых миграций.
- Работа с PostgreSQL имеет свои особенности (право CREATEDB для тестовой базы, поведение транзакции после ошибки целостности), которые нужно учитывать при написании тестов.
- Ограничение уникальности в СУБД надёжнее проверки только в коде: оно работает и при параллельных запросах. Поэтому в тестах проверяется как логика приложения (Cart.add), так и отказ самой базы данных (IntegrityError).
- Покрытие тестами позволяет уверенно дорабатывать проект: любое изменение модели или контроллера сразу проверяется существующим набором тестов.
